HOW TO READ THIS FILE

1. PREREQUISITES
--------------------------------------------------------------------------------
Required:
  * Python 3.11 or newer             (pyproject.toml: requires-python = ">=3.11")
                                     Verified interpreter here: CPython 3.13.5
  * pip
  * SQLite                           (bundled with Python; no server to install)

Check your interpreter (any directory):

launcher if you have it, e.g. `py -3.13 --version`.

5. CREATE THE ENVIRONMENT FILE
--------------------------------------------------------------------------------
Run from: Backend/

PowerShell:

    Copy-Item .env.example .env

Command Prompt:

    copy .env.example .env

Git Bash / macOS / Linux:

    cp .env.example .env

The application reads `Backend/.env` (and the process environment). Every setting
has a safe default, so **no variable is strictly required to start**. Only change
what you need:

  * LATTICE_DATABASE_URL          default sqlite:///./data/lattice.db (relative to
                                  Backend/). Use an absolute URL for anything else.
  * LATTICE_MODEL_ROOTS           approved model directories (default ../models).
                                  Required only when you register a model path.
  * LATTICE_RUNTIME_ADAPTER       auto | llamacpp | fake  (default auto)
  * LATTICE_RUNTIME_ALLOW_FAKE    default false. Must be true to use the fake
                                  runtime, which is TEST ONLY.
  * LATTICE_HOST / LATTICE_PORT   default 127.0.0.1 / 8000
  * LATTICE_AUTO_CREATE_SCHEMA    default true (creates missing tables, never drops)

Never place secrets in `.env` or in this repository: the backend needs none.
`.env` is git-ignored.

6. DATABASE INITIALISATION AND MIGRATIONS
--------------------------------------------------------------------------------
Run from: Backend/

Two supported paths. Choose one; never delete an existing database to "fix"
migrations, and never run `alembic downgrade base` on data you want to keep.

6a. Default: automatic schema creation

    LATTICE_AUTO_CREATE_SCHEMA=true (the default) makes the app run
    Base.metadata.create_all() at startup. It creates missing tables and leaves
    existing rows untouched. It does not record an Alembic version.

6b. Explicit Alembic migrations (recommended for reproducible research runs)

    LATTICE_AUTO_CREATE_SCHEMA=false must be set in `.env` (or the environment)
    before starting the app, then:

PowerShell:

    $env:LATTICE_DATABASE_URL = "sqlite:///C:/absolute/path/lattice.db"
    .\.venv\Scripts\python.exe -m alembic upgrade head
    .\.venv\Scripts\python.exe -m alembic current

Git Bash / macOS / Linux:

    export LATTICE_DATABASE_URL="sqlite:////absolute/path/lattice.db"
    ./.venv/Scripts/python.exe -m alembic upgrade head
    ./.venv/Scripts/python.exe -m alembic current

[VERIFIED HERE] On a fresh temporary SQLite file, `alembic upgrade head` exited 0,
`alembic current` printed `cab7b3235e59 (head)`, and the database contained 11
application tables plus `alembic_version`:
benchmark_measurements, benchmark_metric_summaries, benchmark_runs,
configuration_revisions, configurations, decision_candidates, inference_executions,
jobs, optimization_decisions, workload_revisions, workloads.

Notes:
  * Only one revision exists, so "upgrade from an older schema" is not applicable
    yet. New revisions will be additive; keep applying `upgrade head`.
  * Alembic reads the same `LATTICE_DATABASE_URL` as the app, so set it before the
    command. If you forget, it migrates the default database instead.
  * SQLite foreign keys are enabled on every connection by the app.

9a. Prepare an isolated demo environment

    $env:LATTICE_RUNTIME_ADAPTER = "fake"
    $env:LATTICE_RUNTIME_ALLOW_FAKE = "true"
    $env:LATTICE_GPU_TELEMETRY_ENABLED = "false"

Start the server in that same terminal and leave it running:

    .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

Open a SECOND PowerShell window for the steps below (from any directory). Each
step prints what it received; IDs are kept in variables for the next step.

9b. Credentials-free helper (paste once per window)

    $base = "http://127.0.0.1:8000/api/v1"
    function Post-Json($path, $payload) {
        $json = $payload | ConvertTo-Json -Depth 6
        $json | curl.exe -s -X POST "$base$path" -H "Content-Type: application/json" -d "@-" | ConvertFrom-Json
    }
    function Post-Json-WithHeaders($path, $payload, $headers) {
        $json = $payload | ConvertTo-Json -Depth 6
        $args = @("-s", "-X", "POST", "$base$path", "-H", "Content-Type: application/json")
        foreach ($key in $headers.Keys) { $args += @("-H", "$($key): $($headers[$key])") }
        $json | curl.exe @args -d "@-" | ConvertFrom-Json
    }

`curl.exe` is the real curl shipped with Windows 10/11; do not use the
`Invoke-WebRequest` alias. On macOS/Linux use `curl` instead of `curl.exe`; the
flags are identical.

9c. Step 1 - liveness and capabilities

    curl.exe -s http://127.0.0.1:8000/health | ConvertFrom-Json
    curl.exe -s "$base/capabilities" | ConvertFrom-Json

Expect `status: ok`, and in capabilities: `runtime.adapters` containing `fake`
with `available: true`, `test_runtime_enabled: true`, 14 entries in
`benchmark_metrics`, and hardware fields whose missing values are `null` with a
status reason (never `0`).

9d. Step 2 - create a configuration profile

    $config = Post-Json "/configurations" @{
        name = "demo-config"
        model_id = "demo-model"
        model_format = "gguf"
        quantization = "q4_k_m"
        model_path = "C:\lattice-demo\models\demo.gguf"
        context_length = 2048
        runtime_adapter = "fake"
        generation_defaults = @{ max_tokens = 10 }
    }
    $config | Select-Object id, name, validation_state, model_file_name, model_file_present

Expect HTTP 201 and a UUID. Note that the response deliberately contains
`model_file_name` / `model_path_configured` but never the absolute path.

9e. Step 3 - validate the configuration (preflight)

    Post-Json "/configurations/$($config.id)/validate" @{} |
        Select-Object validation_state, runtime_adapter, runtime_available
    Post-Json "/configurations/$($config.id)/validate" @{} | ForEach-Object { $_.checks }
    Post-Json "/configurations/$($config.id)/validate" @{} | ForEach-Object { $_.preflight.estimate }

Expect `validation_state: valid` and checks for path policy, extension, file
existence and runtime availability. The memory estimate is labelled
`status: estimated`, `method: gguf-file-size-heuristic/1`, `uncertainty: high`,
and the response states that only an actual load is authoritative.

9f. Step 4 - create a workload

    $workload = Post-Json "/workloads" @{
        name = "demo-workload"
        workload_type = "generation"
        input_spec = @{ prompt = "Explain caching in one sentence." }
        output_tokens_target = 10
        context_requirement = 512
    }
    $workload.id

9g. Step 5 - submit a benchmark and poll its job

    $accepted = Post-Json "/benchmarks" @{
        configuration_id = $config.id
        workload_id = $workload.id
    }
    $accepted

Expect HTTP 202 with `status: queued`, `job_id`, `benchmark_run_id`,
`test_only: true`.

    $job = $null
    for ($i = 0; $i -lt 200; $i++) {
        $job = curl.exe -s "$base/jobs/$($accepted.job_id)" | ConvertFrom-Json
        if ($job.status -in @("completed","failed","cancelled","interrupted")) { break }
        Start-Sleep -Milliseconds 200
    }
    $job | Select-Object status, job_type, attempts, error_code

Expect `completed`.

Repeating the *same* submission with the same `X-Request-ID` header is an
idempotent replay: the API returns the original job and run instead of creating a
second one.

    $headers = @{ "X-Request-ID" = "demo-benchmark-key-1" }
    $first  = Post-Json-WithHeaders "/benchmarks" $body $headers   # 202, duplicate: false
    $second = Post-Json-WithHeaders "/benchmarks" $body $headers   # 202, duplicate: true,
                                                                  # same job_id / benchmark_run_id
    (curl.exe -s "$base/benchmarks?include_test_only=true" | ConvertFrom-Json).total

Expect `total: 1`. Reusing that key for a *different* configuration or workload is
rejected with HTTP 409 `conflict` and details naming the existing run, because two
different experiments must never look like one. `X-Request-ID` is generated per
request when the header is absent, so normal clients are unaffected. The same rule
applies to `POST /inference` (same execution replayed) and to job-backed
`POST /optimization/decisions` requests (same decision replayed).

[VERIFIED HERE - real model] two identical submissions returned the same run id,
`duplicate: true` on the second, and `GET /benchmarks` still reported `total: 1`.

Concurrent duplicates are covered too, because the replay check and the insert
run inside one per-key critical section. To reproduce:

    $jobs = 1..8 | ForEach-Object -Parallel {
        curl.exe -s -X POST "$using:base/benchmarks" -H "Content-Type: application/json" `
            -H "X-Request-ID: demo-concurrent-key" -d $using:jsonBody
    } -ThrottleLimit 8

[VERIFIED HERE - real model] eight simultaneous identical submissions returned
one `benchmark_run_id`, seven responses with `duplicate: true`, and exactly one
persisted run. Before the fix the same test produced eight runs (reproduced
three times), which is why the critical section exists. The guarantee is
process-local and matches the single-process job model; a multi-process
deployment would need a database uniqueness constraint as well.

Keys are scoped per job type: reusing a benchmark key for `POST /inference`
creates a new inference instead of replaying the benchmark.

9h. Step 6 - inspect the run, aggregates and raw repetitions

    $run = curl.exe -s "$base/benchmarks/$($accepted.benchmark_run_id)" | ConvertFrom-Json
    $run | Select-Object status, completed_repetitions, failed_repetitions, completed_warmups, test_only, snapshot_hash
    $run.metric_summaries | Select-Object metric_name, status, mean, median, unit, sample_count
    $run.aggregate_summary.counts

    curl.exe -s "$base/benchmarks/$($accepted.benchmark_run_id)/measurements" |
        ConvertFrom-Json | ForEach-Object { $_.items } |
        Select-Object kind, status, sequence, latency_ms, ttft_ms, output_tokens

[VERIFIED HERE] status `completed`, 3 measured repetitions, 0 failed, 1 warmup,
4 raw rows (1 warmup + 3 measured), `test_only: true`. Warmups are stored but
excluded from aggregates. Metrics with no data (for example `quality_score`
without an evaluator, or GPU memory without a collector) show `unavailable` and
null values, not zeros.

9i. Step 7 - request an optimization decision

    $decision = (Post-Json "/optimization/decisions" @{
        workload_id = $workload.id
        candidate_configuration_ids = @($config.id)
        constraints = @(@{ metric = "latency_ms"; operator = "<="; value = 60000; unit = "ms" })
        objective = "minimize_latency"
        evidence_policy = @{ allow_test_only_evidence = $true }
    }).decision
    $decision | Select-Object status, selected_configuration_id, algorithm, algorithm_version
    $decision.candidates[0] | Select-Object feasibility, score, rank
    $decision.candidates[0].constraint_results

Expect HTTP 201, `status: selected`, algorithm `baseline-feasibility-v1`, and a
per-constraint result with `outcome: pass` plus the measured actual value. The
selected evidence is the **most recent** compatible run for the workload
snapshot, protocol version and evidence policy - not simply the oldest one -
so when you have run several benchmarks compare `evidence_run_ids` with the run
you expect to be used. Setting
`allow_test_only_evidence = $true` is required here because this run used the fake
runtime; the default policy rejects it. To see rejection reasoning instead, change
the constraint value to something below the measured latency and re-run: expect
`status: no_feasible_candidate` with reasons, not a fallback selection.

9j. Step 8 - execute the selected decision and validate the actual result

    $execution = Post-Json "/optimization/decisions/$($decision.id)/execute" @{
        prompt = "Execute the selected configuration."
        generation_parameters = @{ max_tokens = 5 }
    }
    $execution

    for ($i = 0; $i -lt 200; $i++) {
        $execJob = curl.exe -s "$base/jobs/$($execution.job_id)" | ConvertFrom-Json
        if ($execJob.status -in @("completed","failed","cancelled","interrupted")) { break }
        Start-Sleep -Milliseconds 200
    }
    $execJob.status

    $inference = curl.exe -s "$base/inference/$($execution.inference_execution_id)" | ConvertFrom-Json
    $inference | Select-Object status, validation_status, prompt_retained, retained_output, latency_ms, output_tokens
    $inference.constraint_results

[VERIFIED HERE] execute -> 202; job `completed`; inference `completed` with
`validation_status: passed`, `prompt_retained: false`, `retained_output: null`,
and constraint results re-evaluated against the actual measurement. If the
decision was not selected, execution is refused (409); if a constraint metric was
not measurable, the result is `not_evaluated`, never `pass`.

The decision-level outcome is a separate, derived read model. It reports the job
and execution state, the post-execution verdict, and every metric next to the
benchmark evidence that justified the decision:

    curl.exe -s "$base/optimization/decisions/$($decision.id)/execution" | ConvertFrom-Json |
        Select-Object verdict, constraints_satisfied, execution_count, job_status,
                      execution_status, baseline_run_id, baseline_available, actual_metrics_available

    (curl.exe -s "$base/optimization/decisions/$($decision.id)/execution" | ConvertFrom-Json).metrics |
        Select-Object metric, direction, baseline_value, actual_value, absolute_delta, relative_delta_pct, improved, reason

`verdict` is one of `not_executed`, `pending`, `constraints_met`,
`constraints_violated`, `completed_unverified`, `failed`, `cancelled`,
`interrupted`, or `execution_missing` (the job is terminal but its execution row
no longer exists, so no verdict can be derived). `improved` is only ever `true` when the measured value actually
moved in the metric's preferred direction; it is `null` when either side is
unavailable. Nothing here is remembered in memory: it is recomputed from the
persisted job, inference execution and evidence run, so it survives a restart.

[VERIFIED HERE - real model] before execution: `verdict: not_executed`, no actual
values. After execution: `verdict: constraints_met`, `constraints_satisfied:
true`, `execution_count: 1`, `baseline_run_id` set, `test_only: false`, and 11
metrics compared. `latency_ms` reported baseline 808.92 ms vs actual 504.18 ms
(delta -304.74 ms, `improved: true`). After a full backend restart the same
endpoint still returned `constraints_met` with the same baseline.

9k. Step 9 - history, comparison and JSONL export

    curl.exe -s "$base/history/summary" | ConvertFrom-Json | ForEach-Object { $_.counts }

    curl.exe -s "$base/history/export?include_test_only=true" -o $outFile
    Get-Content $outFile | Where-Object { $_.Trim() } | ForEach-Object { $_ | ConvertFrom-Json | Out-Null; "record ok" }

[VERIFIED HERE] export returned HTTP 200 with `content-type: application/x-ndjson`
and `x-record-count`; each line parsed as JSON with keys `record_type`,

Comparison (needs two runs; `include_test_only` is not the comparison switch -
compatibility is):

    # submit a second compatible run first, then:
    curl.exe -s "$base/benchmarks/compare?run_ids=$($accepted.benchmark_run_id)&run_ids=<second-run-id>" | ConvertFrom-Json

[VERIFIED HERE] Otherwise-identical test-only runs are reported as
`comparable: false` with `test_only_evidence` and `different_protocol_snapshots`
warnings of severity `blocker` plus per-metric methods. This is intended: fake

9l. Step 10 - error envelopes

    curl.exe -s -o NUL -w "%{http_code}`n" "$base/benchmarks/does-not-exist"

        name = "real-gguf"

12. TROUBLESHOOTING
--------------------------------------------------------------------------------
Command not found: uvicorn / pytest / ruff
  You are in the wrong directory or the venv is not active. Run from Backend/ and
  call the interpreter explicitly: `.\.venv\Scripts\python.exe -m pytest -q`.

"python is not recognized"
  Python is not on PATH. Install it with the "Add to PATH" option, use the full
  interpreter path, or the `py` launcher if available.

Activation blocked in PowerShell
  `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` then activate again.
  This affects only the current shell.

pip install fails
  Check `python --version` is 3.11+. Upgrade pip, then retry. `llama-cpp-python`
  may need a compiler or a prebuilt wheel; it is optional, so the API and tests
  must still work without it.

Alembic errors
  * Set `LATTICE_DATABASE_URL` in the same shell before `alembic upgrade head`.
  * Run from Backend/ (alembic.ini lives there).
  * `alembic current` should print `cab7b3235e59 (head)`.
  * Never delete or reset a database to fix a migration; back it up instead.
  * If tables exist but there is no version row, you previously used automatic
    schema creation. Keep using it, or migrate a fresh database and move your data
    deliberately - do not stamp blindly.

Port already in use
  Change `--port 8010`, or find the owner:
      netstat -ano | findstr :8000
      tasklist /FI "PID eq <pid>"
  and stop only the process you identified.

Missing optional collectors
  Expected. `/capabilities` shows `not_installed` / `unsupported` /
  `permission_denied` with null values. Do not install GPU packages just to make
  the API start.

`503 runtime_unavailable`
  No usable runtime is installed or the fake adapter is disabled. Install
  `llama-cpp-python` and set `LATTICE_RUNTIME_ADAPTER=llamacpp`, or for wiring
  tests only set `LATTICE_RUNTIME_ADAPTER=fake` and
  `LATTICE_RUNTIME_ALLOW_FAKE=true`.

Model path rejected
  The file must exist and live inside an approved root. Set `LATTICE_MODEL_ROOTS`
  to the parent directory and use an absolute path.

Out of memory (`out_of_memory`)
  The runtime could not allocate. Reduce context length, batch size or GPU layers,
  or choose a smaller quantization. Preflight estimates are advisory and may miss
  this. Increase `LATTICE_PREFLIGHT_POLICY=strict` only if you want unknown
  estimates rejected instead of warned.

`409` when cancelling
  Only queued jobs can be cancelled. Native inference is not preemptible, so a
  running job is refused rather than falsely marked cancelled.

`503` on benchmark submission
  The bounded queue is full (`queue_capacity_exhausted`). Wait for jobs to finish or
  raise `LATTICE_JOB_MAX_WORKERS` / `LATTICE_JOB_MAX_PENDING` deliberately.

Tests pass but nothing "real" happened
  Correct - that is the default suite. See section 13.

13. FAKE RUNTIME vs REAL INFERENCE (READ BEFORE CLAIMING RESULTS)
--------------------------------------------------------------------------------
The fake runtime is a deterministic simulator. It exists so the API, database,
job worker, benchmark engine, optimizer and export can be tested offline.

What fake-runtime evidence proves:
  * requests are validated and persisted correctly;
  * jobs run, terminate and recover correctly;
  * repetitions, aggregates, snapshots, decisions, execution and exports are wired;
  * missing data is reported as missing rather than invented.

What it does NOT prove:
  * that llama.cpp can load your model;
  * real TTFT, latency, throughput, memory or quality;
  * that GPU offload actually happened;
  * anything about model output quality.

Every fake run is tagged `test_only: true`, excluded from research history/export
comparisons by default, and rejected as optimization evidence unless
`allow_test_only_evidence` is explicitly set (itself test-only).

To claim real-model inference was tested you need, from one actual run:
  * `test_only: false` on the benchmark run;
  * a populated `model_identity` (path kept private, fingerprint/size present);
  * populated `runtime_metadata` (adapter, version, effective execution mode);
  * `status: completed` (or `partial` with failures explained);
  * measured metric values with `status: measured` (or honest `unavailable`);
  * hardware snapshot with collection statuses;
  * the executed command/environment recorded in section 14.
