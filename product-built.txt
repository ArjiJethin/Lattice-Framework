------------------------------
Execution path: POST /benchmarks → job queued (bounded, capacity reserved BEFORE the row is
persisted) → worker resolves adapter via RuntimeRegistry → LlamaCppAdapter lazily imports
llama_cpp → loads model under a per-key lock → streams generation (TTFT from first streamed
token) → raw measurement rows (warmup kept, excluded from aggregates) → metric summaries with
explicit status/method/reason → run persisted with configuration/workload/protocol snapshots.

No numbers were fabricated; unavailable metrics stay null with reasons.

Metric semantics (code + persisted run evidence): end-to-end throughput and decode
throughput are named and computed from their exact denominators; per-token metrics are
suppressed when token counts are 0/unavailable; device-wide GPU telemetry is never labeled
process-attributed; timeout/failure durations are stored separately from success samples.
Known limitation (documented in capabilities): native llama.cpp decode is not preemptible —
timeouts are enforced between streamed chunks, and cancellation is queued-only.

Mock vs real is rigorously separated: FakeRuntimeAdapter is registered only when
LATTICE_RUNTIME_ALLOW_FAKE=true, its runs are tagged test_only, excluded from list/export
endpoints by default, and rejected as optimization evidence unless explicitly opted in.


H. OPTIMIZATION AUDIT
---------------------
What it genuinely does today (app/optimization/baseline.py, "baseline-feasibility-v1"):
 1. Evidence selection: a candidate is evaluated only against a compatible, sufficiently
   fresh (max_age_hours), allowed-status benchmark run with >= min successful repetitions.
   Test-only evidence is rejected by default. Incompatibility, staleness, missing runs and
   too-few repetitions each produce a distinct persisted rejection code.
 2. Hard constraints gate selection: each constraint (<=, >=, ==) is evaluated independently
   with unit checking; a unit mismatch or missing/estimated metric yields UNKNOWN (never a
   pass); any FAIL makes the candidate infeasible regardless of score.
 3. Deterministic ranking: min-max normalization of objective metrics across eligible
   candidates, weights normalized to sum 1, lower score wins, ties break on configuration id.
   Objectives: minimize_latency, maximize_throughput, or weighted score.
 4. No candidate ⇒ NO_FEASIBLE_CANDIDATE or INSUFFICIENT_EVIDENCE with a persisted reason;
   it never returns a fallback. Execution endpoints accept only a selected, feasible decision
   and validate actual results against the decision's constraints (missing actual metrics →
   not_evaluated, not pass).

This is real constraint-based optimization over persisted benchmark evidence — NOT
placeholders or hardcoded results. What it is NOT: no online/adaptive learning, no Pareto
front computed server-side (the frontend's "Pareto" filter is a client-side
qualityScore>=85 heuristic on fixture data), no multi-objective search beyond the weighted
baseline. Those are honest scope limits, documented as future work.
